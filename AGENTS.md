# AGENTS.md — инструкция для агента

## Начни отсюда

1. Прочитай **`status.md`** — только блок **HANDOFF** (+ соседние секции, если задача шире).
2. **Не читай** `changelog.md`, `about v2.txt`, `update 1.txt`, `tech plan.txt` целиком без необходимости.
3. **`docs/architecture.md`** — только для задач с кодом/архитектурой.
4. В **первом ответе** — блок **«Модель»** и при необходимости **«Переход в другой чат»** с готовым текстом (см. § «Выбор модели»).

---

## Язык (обязательно)

- **Ответ пользователю** — русский, **коротко и по делу**: суть вперёд, без воды; мысли сжато, но понятно. Без лишнего жаргона — кодовые id по-русски («мелкие объекты» вместо `micro`). Имена **файлов** и цитаты **кода** — как в репозитории.
- **Внутренние рассуждения** (thinking) — на родном языке модели, не переводить на русский.

## Выбор модели и переход между чатами (обязательно)

### В каждом первом ответе по задаче

Минимум одна строка:

> **Модель:** `лёгкая` / `средняя` / `сильная` — причина.

### Когда добавлять блок «Переход в другой чат»

Выдавай **полный блок с копируемым промптом**, если выполняется **хотя бы одно**:

| Условие | Куда переходить |
|---------|-----------------|
| Задача требует **сильной**, а разумно считать, что чат «лёгкий» / задача явно про Director, LevelGen, режимы, новый шаг | **Сильный чат** — **до** правок кода |
| Осталась только мелочь (конфиг, 1 файл, docs), а в чате уже тяжёлая фича / длинный контекст | **Лёгкий чат** |
| По ходу работы всплыла связь с архитектурой — **остановись**, не продолжай код | **Сильный чат** |
| Итерация завершена, дальше только тюнинг чисел по playtest | **Лёгкий чат** (промпт на остаток) |
| Пользователь спросил «что дальше» после крупной фичи | Предложи **лёгкий** чат для тюнинга **или** **сильный** для следующего шага — с промптом |

**Не предлагай переход**, если модель уже подходящая **и** чат короткий — напиши: «Переход не нужен, можно продолжать здесь».

### Формат блока (копировать пользователю как есть)

Агент выводит **вне** code block заголовок и пояснения, а **промпт для копирования** — отдельным fenced block `text`:

**Переход в [лёгкий / сильный] чат**

**Почему:** одно предложение.

**Здесь:** продолжай / остановись до переключения — не меняй код.

**Скопируй в новый чат:** *(ниже — целиком в новый чат)*

Шаблон содержимого блока `text`:

    Прочитай Deepseek/status.md (HANDOFF) и Deepseek/agents.md.
    [Тип: лёгкая задача / фича / баг — одна строка.]

    Задача: [конкретное действие одним предложением].

    Читать дополнительно: [только нужное: @файл, architecture.md, §design — или «ничего»].

    Контекст из прошлого чата:
    - [что сделано]
    - [ключевые файлы]
    - [что НЕ трогать]

    Не читай changelog целиком.

Правила для текста внутри блока кода:

- **Задача** — глагол + объект («поднять `drainPerSecond` с 25 до 22», «добавить шаг 12 ракеты»).
- **Контекст** — только то, чего нет в `status.md`; не пересказывать HANDOFF.
- **@файлы** — указывать явно (`@Deepseek/configs/game.default.json`).
- Для **лёгкого** чата: «Только [N] файл(ов), без архитектуры».
- Для **сильного**: перечислить `architecture.md` + нужную § `update1-design.md` + `update1-plan.md` §2.

### Примеры готовых промптов (ориентир для агента)

**Лёгкий — тюнинг после фичи:**
```
Прочитай Deepseek/status.md (HANDOFF) и Deepseek/agents.md.
Лёгкая задача: только конфиг.

Задача: в game.default.json снизить nitro.drainPerSecond с 25 до 22; синхронизировать fallback и схему.

Читать: @Deepseek/configs/game.default.json

Контекст: нитро реализовано в шаге 4; меняем только скорость расхода по playtest.

Не читай changelog целиком.
```

**Сильный — новая механика:**
```
Прочитай Deepseek/status.md (HANDOFF), agents.md, docs/architecture.md.
Фича: шаг 12 UPDATE 1 — ракета.

Задача: реализовать базовый цикл ракеты (бонус, 5 позиций, топливо, возврат в car) по update1-plan §2 и design §12.

Читать: docs/update1-design.md §12–13, docs/update1-plan.md §2 (строки 12–13).

Контекст: машина и конь приняты; V22 закрыт; ракета ещё не начата.

Не читай changelog целиком.
```

### Матрица моделей

| Уровень | Когда | Примеры |
|---------|-------|---------|
| **Лёгкая** | 1–2 файла, без архитектуры, без новой логики | правка чисел в `configs/*.json`; опечатка; обновить HANDOFF; grep по changelog; правка текста в docs |
| **Средняя** | локальный баг, тесты, баланс, 2–4 файла в одном слое | падающий unit-тест; playtest-тюнинг; HUD/оверлей; фикс коллизии в одном модуле |
| **Сильная** | несколько систем, контракты, новая механика, риск регрессии | Director, LevelGen, режимы, musicPatterns, переходы car↔horse; новый шаг UPDATE 1; рефакторинг `core/` |

### Эскалация / деэскалация по ходу

- Лёгкая задача → всплыл Director/LevelGen → **стоп + блок «Переход в сильный чат»** с промптом.
- Крупная фича сдана → в конце ответа **блок «Переход в лёгкий чат»** для оставшегося тюнинга (если есть).
- Сомневаешься средняя/сильная → сильная + узкий промпт в блоке перехода.

## Маршрутизация: что читать

| Тип задачи | Что читать | Модель |
|------------|------------|--------|
| Правка конфига / тюнинг | HANDOFF + `configs/*.default.json` | лёгкая |
| Баг / падающий тест | HANDOFF + test + модуль | средняя |
| Новая фича / геймплей | HANDOFF + `architecture.md` + § из `update1-design.md` + `update1-plan.md` §2 | сильная |
| Playtest / баланс | HANDOFF + последний блок в `changelog.md` по теме (grep) | средняя |
| Архитектура / новый scope | + `../tech plan.txt` §3, при необходимости `about v2.txt` | сильная |
| История «почему так» | `changelog.md` — поиск, не весь файл | лёгкая |

## Автообновление документации (обязательный протокол)

Агент **сам** поддерживает docs в актуальном состоянии. Не ждать напоминания пользователя.

### Когда обновлять

| Событие | Действие |
|---------|----------|
| Завершена итерация / шаг (код + тесты) | `status.md` + `changelog.md` |
| Пользователь **принял** результат playtest | `status.md` (статус → «принят») + `changelog.md` |
| Зафиксировано новое решение пользователя | `status.md` § «Ключевые решения» (1 строка) |
| Закрыт / открыт вопрос | `status.md` § «Открытые вопросы» |
| Изменился контракт системы | `docs/update1-design.md` — только затронутая § |
| Сменился текущий шаг плана | `docs/update1-plan.md` §2 (статус строки) |
| Только мелкая правка без смены этапа | **не** раздувать changelog; при необходимости 1 строка в HANDOFF |

### Что писать куда

**`status.md`** (коротко, <80 строк целевой лимит):

- HANDOFF: где мы / следующее действие / не трогать / последние проверки (N/N тестов).
- Таблица «Текущее состояние» — одна строка на область.
- Дата обновления.

**`changelog.md`** (детально, в **начало** файла, сразу после заголовка):

```markdown
### [дата] — Краткое название итерации — статус (реализовано / принято / …)

- Что сделано (буллеты).
- Ключевые файлы/модули.
- Tunables / конфиги, если менялись.
- Проверки: typecheck ✓, lint ✓, unit N/N ✓, e2e …
```

Старые записи **не удалять** — только prepend новых.

**Не дублировать**: длинные списки параметров — только в changelog; в status — итог одной фразой.

### Порядок в конце сессии

1. Прогнать `typecheck` + `lint` + `test` (если менялся код).
2. Обновить `status.md` (HANDOFF + таблица + дата).
3. Добавить блок в начало `changelog.md` (если была значимая работа).
4. При необходимости — точечно `update1-design.md` / `update1-plan.md`.
5. В ответе пользователю: что обновлено в docs (одна строка).

### Чего не делать

- Не копировать весь ответ чата в changelog.
- Не раздувать `status.md` историей (история → changelog).
- Не обновлять docs «на будущее» для несделанной работы.

## Для пользователя (как пользоваться переходами)

Агент **сам** предложит переход и даст блок **«Скопируй в новый чат»** — тебе нужно только:

1. Открыть новый чат с нужной моделью (лёгкой / сильной).
2. Вставить текст из блока целиком.
3. При необходимости добавить `@` на файлы из блока.

Переход **не обязателен**, если агент написал «Переход не нужен».

## Проект

Браузерный lane-based 3D-раннер «Music Director Runner». Музыка через Director меняет параметры мира, но НЕ генерирует уровень. Стек: TypeScript + Vite + Three.js + Zod, Vitest, ESLint. Папка: `Deepseek/`.

## Как работать

- Одна веха/шаг за раз.
- **Неоднозначности — уточняй у пользователя до правок** (см. § «Уточнения у пользователя» ниже). Не угадывай intent, если разумно возможны 2+ трактовки.
- Коммиты git — только по явной просьбе.
- Язык общения: русский, кратко. Рассуждения модели — на её родном языке (см. § «Язык»).
- После правок кода — как проверить вручную.

---

## Уточнения у пользователя (обязательно)

**По умолчанию спрашивай**, если пункт задачи можно понять по-разному. Лучше один короткий вопрос до кода, чем переделка после.

### Когда спрашивать (не молча выбирать вариант)

- **Feel / баланс / «сделай лучше»** без чисел или критерия («плавнее», «мощнее», «реже»).
- **Несколько равнозначных реализаций** (архитектура, где класть логику, новый конфиг vs хардкод).
- **Scope не ясен**: только то, что в промпте, или соседние системы тоже?
- **Поведение на границах**: что если топливо кончилось / игрок в horse / два бонуса рядом — в промпте не сказано.
- **Визуал и UX** без референса: форма, цвет, интенсивность VFX, длительность перехода.
- **Конфликт** между промптом, `status.md`, design и кодом — что приоритетнее?
- **Playtest-фидбек** расплывчатый: «странно», «не то» — уточни *что именно* (момент, режим, полоса, тайминг).

### Когда можно не спрашивать

- Ответ однозначно следует из **`update1-design.md` / HANDOFF / явного промпта**.
- Мелкая очевидная правка (опечатка, падающий тест с ясной причиной).
- Выбор **дефолта из проекта** (паттерн соседнего кода, Zod+fallback, тот же слой архитектуры) — **кратко напиши в ответе**, какой дефолт взял и почему.

### Как спрашивать

- **1–2 вопроса за раз**, не анкета на 10 пунктов.
- Давай **2–4 конкретных варианта** (+ «другое»), с пометкой **(рекомендую)**, если один явно лучше по архитектуре проекта.
- Если вопрос блокирует работу — **остановись до ответа**, не пиши большой diff «наугад».
- Если не блокирует — можно сделать минимальный безопасный шаг и явно пометить **открытый вопрос** в ответе.

### Чего избегать

- Не раздувать уточнения по уже зафиксированному в design/status.
- Не спрашивать ради спрашивания (формальности, общие «подтвердите план» на тривиальной задаче).
- Не маскировать угадывание под «я решил, что вы имели в виду…» без пометки допущения.

## Быстрая экономия токенов (для пользователя)

Уже сделано: короткий `status.md`, `changelog.md` вне индекса, handoff-промпты, `.cursorignore` (папка `arch/`, `node_modules`, медиа).

**Ещё 5 минут — максимум эффекта:**

| Действие | Зачем |
|----------|--------|
| Workspace = папка **`Deepseek/`**, не весь `Runner/` | агент не видит 3 GB `arch/` |
| В промпте **`@конкретный_файл`**, не `@папка` и не `@codebase` без нужды | меньше мусора в контексте |
| Не вставлять длинные логи playtest — 3–5 буллетов «что не так» | экономия на каждом сообщении |
| Держать **2 чата**: главный (сильная) + сервисный (лёгкая) | не раздувать историю |
| Мелочь (одно число в конфиге) — **лёгкая модель + короткий чат** | в 5–10× дешевле сильной |

**Не обязательно сейчас (если понадобится):**

- Архивировать §3+ в `update1-plan.md` (~100 KB) в `changelog.md` — как со `status`.
- В Cursor Settings отключить лишние MCP, если не пользуешься.
- Длинный контекст / Max Mode — только для больших фич, не для тюнинга.

**Агенту:** не вызывать broad search по `arch/`, `node_modules`, `changelog.md` целиком; grep с `head_limit`.
